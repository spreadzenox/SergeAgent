# Contexte du projet au 27 septembre 2026

Résumé compact de la longue discussion de revue menée avec Julien puis
Clem (septembre 2026, branche `Clem`), pour qu'une nouvelle session, humaine
ou LLM, puisse discuter du projet sans tout relire. Le détail de chaque
décision est dans [`DECISIONS_REVUE.md`](DECISIONS_REVUE.md) (Q1 à Q59) ;
l'état du chantier en cours est dans [`REPRISE_LOT6.md`](REPRISE_LOT6.md).

## Les personnes

- **Julien** : propriétaire de Serge et du serveur où il tourne. Il valide
  les décisions importantes par ticket Discord.
- **Clem** : frère de Julien, a repris la revue après le lot 5. Il a posé
  la règle « le code n'est qu'un interpréteur de la base » et le style des
  documents.

## Serge en bref

Un agent économique autonome, organisé en une chaîne de 8 étapes :
pré-prospection, conception du POC, prospection légère, choix du business
principal, construction, prospection lourde, mémoire, caisse. Il cherche des
besoins sur le web, teste des business auprès de vrais prospects, garde le
meilleur, le construit, le vend et encaisse. Sa seule limite est la
légalité ; il assume d'être un agent IA. Mission Control (MC) est sa
console web ; SQLite (`state/serge.db`) est la seule source de vérité.
Chaque fusion dans `main` redéploie Serge sur le serveur de Julien.

   le prix.

## Les décisions qui structurent la suite

- **Le code n'est qu'un interpréteur de la base (Q54, Q56).** L'ordre des
  invocations et tous leurs paramètres sont en base, jamais en dur. Le code
  est rangé par capacité (lire, écrire, appeler un modèle, web, bac à
  sable, API décrite en base, canal, ticket), jamais par invocation. Même
  l'écriture est générique, avec des protections réglées en base (tables
  autorisées, changements de statut permis, doublons). Le nom d'une
  invocation n'apparaît que dans `config/pipeline.yaml`. À terme, un
  éditeur sans code dans MC permettra de créer une invocation de toutes
  pièces. Vaut pour tous les lots futurs, y compris le bac à sable et
  l'agent web.
- **La base fait foi (Q2, Q3).** Le YAML ne sert qu'à remplir une nouvelle
  instance ; rien n'est écrasé ; un objet supprimé dans MC ne revient pas.
- **Le runner (Q51).** Une file de priorité où s'ajoutent les invocations
  déclenchées (idée de Julien, gardée), mais deux files en parallèle
  (conversations, travaux), une tâche après l'autre, enregistrée après
  chacune. L'ancien runner pouvait envoyer deux fois le même e-mail.
- **Répondre aux prospects (Q37, Q38, Q50).** Un fil par prospect ; une
  seule invocation « Traiter une réponse » qui reçoit le fil, la fiche du
  prospect, celle du business et une fiche produit détaillée (validée par
  Julien) ; jamais de relance à quelqu'un qui a répondu ; tickets
  compréhensibles sans suivre Serge ; délais de réponse réglables par canal
  (Q52).
- **L'agent vocal (Q53).** Cherche le numéro en base au décrochage ; sinon
  « Bonjour, je suis Serge, en quoi puis-je vous aider ? » et recherche par
  tool ; refuse poliment les propositions entrantes pour l'instant.
- **Les places (Q14).** 3 tests légers, 1 business principal, pas de file
  d'attente. Nouveaux statuts `PARKED`, `MAINTENANCE`, `CLOSED` (Q44).
- **Mesure (Q16).** Une grille de points par canal ; on compare total et
  points par euro.
- **Web (Q48).** Gratuit d'abord (SearXNG, Playwright, Browserbase en
  dernier recours), LinkedIn avec validation humaine de chaque message.
  Pas de contournement de la détection de robots.
- **Lot 6 (Q57, Q58, Q59).** Une seule table d'invocations ; modèle choisi
  seulement par niveau ; pipeline de départ dans `config/pipeline.yaml` ;
  historique des réglages plus tard ; doublons « identique » et « mots en
  commun » pour commencer. Pas de transition : l'ancien code en dur est
  rangé dans `pas_encore_branche/`, pas détruit. On ne crée que les
  colonnes utiles au lot. Serge ne peut pas être allumé pour de vrai tant
  que toutes les capacités ne sont pas là ; c'est accepté.

## Façon de travailler

- Français simple, phrases courtes, exemples concrets, pas de jargon
  (« hôte », « jonction », « canon », « contrat »…). Vaut pour la doc, le
  TODO et la conversation.
- TODO : une case, un titre en gras, un paragraphe descriptif.
- Une question à la fois pendant les revues ; chaque réponse validée fait
  foi et est notée dans `DECISIONS_REVUE.md`.
- Commits en français (ce qui change, pourquoi, comment on vérifie) ;
  fusion dans `main` par pull request, tests verts seulement.
